## 1. Purpose

Nothing runs in production. The screens and the API are built and tested on a laptop, staging is a Supabase project in Mumbai patched by hand, and the demos are served from the operator's own machine on port 3100. That is fine for showing the work and impossible for a practice to depend on: there is no address a household can be given, no deploy that is not a person typing commands, no backup anybody has ever restored, and nothing that says the API has stopped except somebody noticing. This piece gives the platform an address, a way to be deployed by tagging a version rather than by hand, a backup that has been proved by restoring it, a check that notices when it is down, and the deep security scan that was started once and never finished. It deliberately separates everything that can be built now from the one question that belongs to the founder's lawyer.

## 2. The three confirmations, with what the API answered

Read-only calls only: listing and reading, nothing that creates, deploys, links or changes. The account holds one hosting order, `1009508471`, plan `hostinger_premium_v3`, status `active`, and one hosting subscription, "Premium Web Hosting", next billing 2030-07-29. Four websites sit on it, all under the one username: `mcwellnessuae.com` (main), `intake.mcwellnessuae.com` and `qeeg.mcwellnessuae.com` (subdomains) and `gulflens.net` (addon). The platform would be the fifth, as the operator said.

**2.1 Does the plan run a persistent Node.js application? Not confirmed, and it must not be assumed.** The API's answer is mixed and none of it is a yes. Every one of the four sites reports `"website_type": "other"`, and asking the API for this account's Node.js sites (`website_types=nodejs`) returns `{"data":[],"meta":{...,"total":0}}` — nothing on the account is a Node.js application today. The Node.js pipeline endpoints do answer for this website rather than refusing it, which is the one encouraging sign: builds return `{"data":[],"meta":{"total":0}}` and environment variables return `[]`, while build settings return `{"message":"[Hosting:9999] Not found."}`, which that endpoint's own documentation says is the expected answer "until the first build or the first settings update stores them" rather than a plan restriction. Against that, the plan's actual runtime reads as ordinary shared PHP hosting: PHP 8.3.33 under CloudLinux `alt-php` (`include_path` default `.:/opt/alt/php83/usr/share/pear:...`), with `disable_functions` defaulting to a list that includes `system, exec, shell_exec, passthru, proc_open, popen`, and with both `pgsql` and `pdo_pgsql` reported `"state": "disabled"`. Hostinger's own pages disagree with each other: `hostinger.com/web-hosting` lists Node.js among the Premium plan's "Build with" items, while `hostinger.com/nodejs-hosting` sells persistent Node.js as two different products — "Web Apps Hosting" and a VPS — and describes neither as the shared tier. Nothing readable through the API establishes the property the platform actually needs, which is not "Node.js exists" but **always-on**: one long-lived process that keeps a Postgres connection pool warm between requests, holds the rate limiter's counters in its own memory (`docs/SECURITY.md` layer 3), and stays up when nobody is asking for a page. A managed runtime that starts a process per request, or sleeps it when idle, satisfies none of that. So this is written as an open decision rather than a plan, with the alternatives priced in section 3 and the recommendation at decision 1.

**2.2 Which data centre? Not the UAE, and the exact one is not exposed by the read calls.** Asked which data centres are available to this order, the API returned fourteen: Boston, North Carolina, Phoenix, Singapore, the Netherlands, Lithuania, the United Kingdom, Mumbai, Brazil, Indonesia, France, Frankfurt, Kuala Lumpur and Dusseldorf. **There is no UAE location on the list**, exactly as the plan expected, and of the fourteen the nearest to Dubai is Mumbai. Which of them the existing order sits in is not something the listing or reading calls report — that list is what is offered for setting up, not where the plan is — so it stays a confirmation the operator reads in hPanel. What matters more than the exact answer is the pairing: the database, the sign-in service and the documents are on Supabase in Mumbai (`ap-south-1`), and this API is database-heavy, with most screens costing several round trips. A web tier in Boston or Frankfurt puts an ocean between the process and its database on every one of them. **Put the web tier in Mumbai**, beside the database, whatever runs it. That is a few milliseconds instead of a few hundred, it is also the closest of the fourteen to the households being served, and it changes nothing about the region question, because the personal data already rests in Mumbai and this only moves the process that reads it.

**2.3 What Hostinger would receive.** Everything, in the clear, at its edge. Hostinger terminates TLS and fronts the sites with its own content delivery network — the `intake` and `qeeg` subdomains already resolve through `*.cdn.hstgr.net` ALIAS records, so the CDN is demonstrably in the path today. Serving `app.mcwellnessuae.com` would therefore mean Hostinger sees each request's caller address, path and query string, headers and cookies, and both request and response bodies: for this platform that is household names, telephone numbers, addresses, visit times and windows, ledger amounts, and the fact that a named person consented to something. It also keeps access logs. Two consequences follow for the build. First, `docs/SECURITY.md` layer 1 requires query strings to be stripped from `/api/*` access logs, because a search term is typed by staff about a client — we control that in our own process, and at a shared host's edge we very likely do not, which is a limitation to record rather than a thing to fix. Second, `TRUSTED_PROXY_HOPS` must be set to exactly the number of proxies in front of the API, and with the CDN in the path that is at least one; it is measured on the first deploy, never guessed, because too few makes every caller share one rate-limit budget and too many makes the address attacker-chosen. No data at rest reaches Hostinger: the database, the sign-in service and the documents stay on Supabase.

## 4. The pipeline

No deploy workflow exists today; `.github/workflows/` holds `verify.yml` (pull requests and pushes to `main`) and `audit.yml` (weekly). Neither is triggered by a tag, and the only tag ritual in the repository, `trunk-v1` in `docs/STAGING.md` section 7, is consumed by nothing.

**4.1 The trigger.** A new `.github/workflows/release.yml` on `push: tags: ['v*']` and nothing else. Pushing `v1.0.0` is the act that deploys; there is no deploy button, no branch that deploys itself, and `main` moving does not reach production.

**4.2 The steps.** Checkout, pnpm from `packageManager`, Node from `.nvmrc`, `pnpm install --frozen-lockfile`, then `pnpm verify` and `pnpm audit:deps` with `AUDIT_DEPS_STRICT=true` — a release does not get the pull request's excuse for an npm advisory outage. Then `pnpm exec vite build --mode production`, which produces `dist/`. The build bakes `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` into the bundle, and `docs/STAGING.md` section 6 already records why the `--mode` flag is not optional: a plain `pnpm build` reads the wrong environment file and the sign-in page falls back to the laptop door. Then migrations (section 5), then the upload, then one call to `/api/health` against the live address, and the workflow fails if it does not answer.

**4.3 What ships.** `dist/`, the API's source, and the dependency tree. Note a real snag for the builder: `pnpm start` runs the API's TypeScript through `tsx`, which is a **development** dependency, so an install of production dependencies alone leaves the API unable to start. Decision 3 takes the simple way out.

**4.4 Secrets, and where they are not.** Two stores, neither of them the repository. The pipeline's own credential — whatever the chosen host authenticates a deploy with — lives in a GitHub Environment named `production`, which also gives a deployment record and a place to require the operator's approval (decision 7). The API's runtime settings live in the host's own secret store, set once by the operator and never passing through GitHub or through Claude: `APP_ENV=production`, `SUPABASE_URL`, `SUPABASE_JWKS_URL`, `SUPABASE_JWT_SECRET`, `API_DATABASE_URL` (the pooler form, as the `mcwellness_api` role), `IDENTITY_KEY` (freshly generated, one per environment, never staging's), `STORAGE_PROVIDER=supabase`, `SUPABASE_STORAGE_KEY`, `SUPABASE_AUTH_ADMIN_KEY`, `SERVE_APP=true`, `HOST`, `PORT`, `TRUSTED_PROXY_HOPS`, `PUBLIC_APP_URL=https://app.mcwellnessuae.com`, and piece eight's `ROUTING_PROVIDER` and `GOOGLE_MAPS_API_KEY`. `.env.example` gains a comment naming production as a third environment and keeps placeholders only; `pnpm verify`'s secrets scan is what enforces that, and it runs on every change.

**Amended in the build, 2026-09-06** (the integrator's second note on this file's pull request): one credential does pass through GitHub after all, and it is not one of the API's — section 6's weekly dump runs from a GitHub workflow, so the dump's own database credential, a separate read-only one that can read the rows and change nothing, lives in GitHub's secret store beside the pipeline's, while every runtime setting listed above still stays with the host and never enters GitHub.

## 5. The production guard for `pnpm db:migrate`

There is no guard today. `db/migrate.ts` reads `DATABASE_URL` through `requireDatabaseUrl()` (`db/runner/apply.ts:24`) and connects to whatever it names — which is exactly how staging is patched. A production database on the end of that is one mistyped environment file away from being migrated by a session that thought it was local.

The guard goes in `db/migrate.ts` immediately before `connect()`, in the shape `db/reset.ts:16-26` already uses for the reset command, and refuses when the URL names the production project unless **both** conditions hold: `MIGRATE_TARGET=production` is set, and the revision being migrated is the `v*` tag the release is deploying, so the release workflow can migrate and a laptop cannot. The pure rule joins `isLocalDatabaseUrl` in `db/runner/plan.ts` (around line 265) with its own tests; the message and the I/O join `describeDatabase` in `db/runner/apply.ts:33`, which prints host, port and database name and never the URL, because the URL carries the password. The refusal is a plain sentence naming the database it declined and what would have allowed it. Two tests: the deny case, and the allow case with both conditions met. Separately, `.claude/hooks/no-prod-in-dev.sh` gains the production project's reference, which its own comment has been asking for since it was written.

**Amended in the build, 2026-09-06** (the integrator's first note on this file's pull request): this guard stops a mistake and not a determined person. Whatever tells `db:migrate` which tag it is running — an environment variable the workflow sets, and the tags on the checked-out revision — can be arranged on a laptop too by somebody who means to. That is the right size for one practice: the thing being prevented is a session or a shell that believed it was pointed at a local database, not sabotage.

**Amended in the build, 2026-09-06** (the shape the build took, which is Claude's default and goes beyond the wording above): the rule is written the other way round, because no production project reference exists yet to match a URL against. **Any database URL that is not local is refused unless `MIGRATE_TARGET` names it** — `staging` or `production` — and `production` additionally requires `RELEASE_TAG` to be a `v*` tag that the checked-out revision actually carries. This is the honest shape of "a laptop cannot": it needs no list of hosted projects to be complete, and it fails closed for a database nobody has named. When the production project is created, its reference is added in one place, `.claude/hooks/no-prod-in-dev.sh`, and this rule is unchanged.

## 6. Backups, and a restore that has actually been done

Two independent copies, because one copy in the same account as the original is a convenience, not a backup. First, Supabase's own daily snapshot, which the Pro plan the organisation is already on provides — this is the fast path for "yesterday was fine". Second, a weekly `pg_dump` written to a private `backups` bucket in a **second** Supabase project in a different region, so that losing an account, a project or a region does not take both copies. Weekly dumps are kept ninety days (decision 6) and the job that writes them is a scheduled GitHub workflow, since GitHub is already on the vendor register and the dump never passes through anybody new.

The rehearsal is the point, not the dump. Once before the first production deploy and quarterly thereafter, the newest weekly dump is restored into a scratch Supabase project and checked: the migration table's row count, the schema fingerprint compared against a fresh local build the way `docs/STAGING.md` already compares it, the audit chain verified, and the exit test of `docs/STAGING.md` section 7 walked. The date, the dump's size, how long the restore took, what was checked and anything that went wrong are written into a new `docs/RUNBOOK/restore.md`. A backup nobody has restored is a belief.

One honest limitation to record rather than solve: an erasure request removes a household from the live database, but a dump taken before it still holds those rows until it ages out. Ninety days bounds that, and the runbook says in one line that a restore is followed by re-applying any erasure raised since the dump was taken.

## 7. Monitoring

**7.1 Uptime.** An external check on `https://app.mcwellnessuae.com/api/health` every few minutes, which must be able to wake the operator rather than only draw a graph (decision 5). The route is at `app/api/create-api.ts:172`, public and registered before the authentication fence, and answers `{"ok":true,"service":"mcwellness-api"}` — deliberately carrying nothing environment-specific, which is also why the checker receives no personal data and is an easy vendor row.

**7.2 The health check does not see the database.** `/api/health` touches no connection, so it stays green through a complete Postgres outage: the screens would be broken and the monitor happy. This piece adds a second route, `/api/health/deep`, which takes one connection from the pool, runs `SELECT 1`, and answers ok or not-ok and nothing else — no version, no host, no error text, so a caller learns whether the practice's system is working and nothing about its shape. It is rate-limited and unauthenticated. `/api/health` is left exactly as it is, because the deploy step and any load check want a route that cannot fail for a reason outside the process.

**7.3 Errors, without a tracker.** `CLAUDE.md` rule 9 forbids analytics SDKs and error trackers, and rule 5 forbids logging personal data to console, error trackers or APM; the vendor register repeats it. So no Sentry, no APM agent, nothing in the bundle. What we do instead: the API writes one structured line per unhandled error to stderr — a request identifier, the route pattern, the status, the duration and the error's class, with no query string, no body and no identifier belonging to a person — and the host retains those lines where the operator can read them. Anything that touched personal data is already in the audit trail, which is the record that matters. Between the audit trail, the error lines and the uptime alert, an outage is noticed and diagnosable without a single third party receiving a household's data.

## 8. The dependency audit, already in place

Nothing to build. `.github/workflows/audit.yml` runs `pnpm audit:deps` every Monday at 04:00 UTC with `AUDIT_DEPS_STRICT=true`, and `verify.yml` runs it non-strict on every pull request, so an npm advisory outage cannot block a merge but cannot hide a vulnerability either. This piece's only addition is section 4.2's strict run inside the release, so a tag cannot ship a known high or critical vulnerability in a production dependency.

## 9. The deep security scan

Run the `claude-security` plugin's scan to completion, in its own session, against the exact revision the first release tag names — not against `main`, which moves. It is expensive, so it belongs in a session of its own under the cost rules of `docs/HANDOVER.md` section 6, and it is the last gate before the first deploy rather than a thing done alongside the build. Its findings are triaged rather than applied: each accepted one becomes its own small pull request with the combined review and the re-check the house already uses, each rejected one is recorded with the reason it was rejected, and the scan's report and the revision it ran against are written into the pull request record. A scan whose findings were never verified is worth less than no scan, because it produces confidence without evidence.

## 10. What the lawyer's answer changes, and what it does not

Everything in sections 4 to 9 is written so that the region is a setting. The pipeline, the migration guard, the backups and the rehearsal, both health routes, the error lines, the audit and the security scan are identical whatever the answer, and all of them can be built now.

What the answer decides is only where two things are created: the Supabase region for the production project, and the Hostinger data centre for the web tier. One sequencing point makes this load-bearing rather than academic: **a Supabase project's region cannot be changed after it is created**, so the production project is not created until the lawyer has answered. Creating it in Mumbai now and moving it later is not a setting change, it is a new project and a migration of every row and every file.

If the answer is that Mumbai is acceptable — which `docs/ADR/0003` reads as defensible, the business being a wellness company rather than a licensed clinic, and the consent wording telling the household where the data is held — then this piece is finished as written. If the answer is that personal data must remain in the UAE, then neither vendor can serve it: Supabase has no UAE region and Hostinger has no UAE data centre, and the plan's own answer applies, which is Amazon's UAE region with the database and the sign-in service run by us, and about a further week's work. Nothing in this piece is wasted in that case except the Hostinger row.

## 12. Deliberately left out

More than one instance of the API. The rate limiter's counters live in this process's memory (`docs/SECURITY.md` layer 3), so a second instance silently halves every limit; a shared store would fix it and is itself a vendor question, and one practice does not need it. A deploy pipeline for staging, which stays hand-patched as `docs/STAGING.md` describes until production is proved. Zero-downtime or blue-green deploys: a restart of a few seconds, taken at night, is honest and much simpler. Automated rollback — the previous tag is the rollback, and the real constraint is that migrations are forward-only, which is why each carries its `-- rollback:` block for a human. Log shipping to a third party, and any hosted APM. Infrastructure as code: one site on one plan is configured by hand once and written down, not templated. Hosting for background jobs, because there are none — `pg-boss` is named in `CLAUDE.md` and in the plan but is not a dependency today, and the one job that exists is run by hand; when jobs arrive, whether the host can run them becomes part of decision 1 rather than an afterthought.

## 13. Decisions, with the defaults taken

1. *Where the API runs.* This one is the operator's, and it is put first because section 2.1 could not confirm what the plan assumed. Default (Claude's): **do not bet the first deploy on the Premium plan.** Move the platform to Hostinger's managed Node.js product on the same account, in Mumbai, which keeps one vendor, one bill and one register row, and costs what section 3's table says. Ask Hostinger in writing about the Premium plan in parallel; if the answer is a genuine always-on process, the saving is discovered rather than assumed and the move is undone cheaply. The rejected alternative is splitting the screens from the API to use the plan already paid for: it saves a few dollars a month and costs the property `docs/SECURITY.md` layer 2 depends on, which is that one process serves both, so the same protective headers cover the screens as cover the data; it also introduces a cross-origin boundary where none exists today.
2. *Which data centre.* Default (Claude's): Mumbai, beside the database, for the reason in 2.2. Not a region decision, a latency one.
3. *Compiled, or `tsx` at runtime.* Default (Claude's): install development dependencies in production and keep `tsx`. It is one dependency, audited weekly, and it keeps the production start command identical to the one used everywhere else, which is worth more than the disk it costs. Compiling the API ahead of time is the tidier answer and can be taken later without changing anything else.
4. *Where the second backup lives.* Default (Claude's): a private `backups` bucket in a second Supabase project in a different region. No new vendor, no new register row, and a different region and project from the original, which is what independence means here.
5. *The uptime checker.* Default (Claude's): a hosted uptime service that can wake the operator, added to the register as receiving no personal data (2.3 and 7.1). The no-vendor alternative, a scheduled GitHub workflow that calls the route, was considered and rejected: scheduled runs are delayed under load and nothing they do reaches a phone at two in the morning.
6. *How long backups are kept.* Default (Claude's): weekly dumps for ninety days, daily snapshots as the plan provides. Long enough to survive a fault discovered late, short enough that section 6's erasure limitation stays bounded.
7. *Who releases.* Default (Claude's): the `production` GitHub Environment requires the operator's approval, so pushing a tag proposes a deploy and a person releases it. The alternative, a tag deploying unattended, is faster and removes the last human look before a household's system changes.
