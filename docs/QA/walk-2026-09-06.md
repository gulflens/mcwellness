## Defects and other findings

Every numbered defect below is repeated in `docs/CHANGE-REQUESTS/qa-01.md`
with its own file references.

1. No manual "confirm" control exists anywhere (UI or API) to move an
   appointment from `proposed` to `confirmed`, despite
   `docs/SPEC/scheduling-manual.md` section 3 naming one ("manual toggle
   in Phase 1"). Every appointment created through "Add appointment"
   stays Proposed forever. Screen: Schedule (`app/admin/schedule/
   SchedulePage.tsx`), only "Move" and "Call off" are offered.
2. The laptop's own keep-alive script
   (`.../scratchpad/keepalive.py`) checks port 5173's liveness against
   `127.0.0.1`, which Vite never binds in this environment (see "Before
   the walk"); the check therefore always reads "down", and the script
   kills and restarts the whole `pnpm dev` stack every sixty seconds,
   forever — confirmed continuously since 05:06 in `keepalive.log`. This
   caused repeated mid-request `ERR_CONNECTION_REFUSED` and `502 Bad
   Gateway` responses and silently closed open forms throughout this
   walk. Not a product screen; flagged for whoever maintains that script.
3. A progress-report draft says "This client has fewer than two brain
   maps of one kind, so the report says nothing about them" for a client
   with two brain-map assessments on file (the same two the Compare
   screen correctly finds and compares). Screen: Reports tab, "Write a
   progress report".
4. The client search box ("Name, record number or Emirates ID", used on
   Clients and inside "New appointment") answers "No client matches" for
   a client's full display name typed with a space (e.g. "Dahlia Bay"),
   while the given name alone ("Dahlia") and the record number
   ("MW-000005") both match correctly.
5. Calling off a still-**Proposed** appointment — "client not yet
   informed" in the scheduling spec's own words — can still show "This
   is inside the practice's 24 hours' notice, so it uses one of the
   client's sessions" and offers "The family called it off" as a reason,
   which cannot be true of a visit the family was never told about.
   Screen: Schedule, "Call off" drawer.
6. Grammar: the client Timeline reads "Hazel Harbour **added a**
   appointment" (missing "n"). Generic fallback template,
   `domain/shared/audit-narrative.ts` line 828 (`${actor} added a
   ${entity}`), does not choose "an" for a vowel-leading entity name.
7. Neither seeded "Client contact" person (Dahlia Bay, Clover Quarry) can
   sign in through the laptop's own sign-in door: `/api/me` answers 403
   and the screen shows nothing. A direct, read-only check of the local
   database confirmed the cause: `app_user` holds no row at all for
   either name, even though `GET /api/dev/session` lists them by name
   (it calls the current seed generator in memory; it does not read the
   database). This local database appears not to have been reseeded
   since the client-portal contacts were added to `db/seed`
   (`docs/STAGING.md`'s own record of that change). The same staleness
   likely explains the empty Kit register (piece eight, item 3) and the
   portal's own "The practice has not recorded a WhatsApp number", both
   of which `docs/STAGING.md` records as already seeded elsewhere. Not
   filed as a stream's code defect on the evidence gathered; flagged for
   whoever next reseeds the laptop's database. The real invite-and-redeem
   door works correctly and was used instead for the rest of the walk.
