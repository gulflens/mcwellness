# Debtors List Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Billing › Balances opens on a debtors list. It shows who owes the
practice, split into 0–30, 31–60, 61–90 and over 90 days, with totals and a
CSV download. Each household also gets a downloadable statement of account
PDF.

**Architecture:**
- The pure allocation and ageing rules live in `domain/billing/ageing.ts`.
- One route module reads `app.billing_ledger` plus the invoice each payment
  or credit note names, and computes in memory.
- A statement document renders on demand and is not filed.
- No migration.

**Tech Stack:** TypeScript, Hono, React + Vite, PostgreSQL (row security),
Vitest.

**Spec:** `docs/superpowers/specs/2026-10-23-debtors-design.md`. Read the
"Decisions" table and "The allocation, exactly" section first.

## Global Constraints

- Money is integer fils. The browser does no arithmetic on money; every
  figure comes from the server.
- The buckets are, in days from the invoice date to as-at: 0–30, 31–60,
  61–90 and over 90.
- Who may read: owner, admin, lead practitioner and finance
  (`mayReadInvoices` in `app/api/billing/access.ts`). Anyone else gets 403.
- Erased households are excluded from the list. A statement for one is 404.
- Audit:
  - each list row shown writes one `list` audit row (`logReads`, entity
    `billing_ledger`);
  - the CSV writes one `list` row per exported row plus one `export` action;
  - a statement writes one audited read (`logRead`).
  - The list page holds at most 50 rows.
- No household's name, and no other personal data, in a URL or a log.
- CSV uses `domain/shared/csv.ts` `toCsv`, which escapes formulas, and
  `csvResponse`.
- The statement heading is exactly `Statement of account` / `كشف حساب`. New
  Arabic strings carry an `OWNER REVIEW` comment. The statement uses no "Tax"
  wording.
- UI follows `docs/DESIGN-BRIEF.md` and `.claude/rules/ui.md`:
  - token colours;
  - logical CSS properties;
  - tables;
  - a right-side drawer;
  - no ALL-CAPS labels.
- Fixtures come from seed generators or synthetic names. No lawyer or
  legal-review dependency appears anywhere.

## Review Focus

1. **A payment made before its invoice existed** (a package prepaid) pays
   that invoice, so the household shows as current, not as credit plus a
   debt. The test is in Task 1.
2. **A household's list total equals its single-household balance**, for
   every seeded household. The test is in Task 2.
3. **A waived fee that a payment names** is not in the ledger. That payment
   joins the pool and is not lost. The test is in Task 1.
4. **As-at a past day** ignores everything dated after it, including credit
   notes issued later. The test is in Task 2.
5. **A CSV cell that starts with `=`** (a synthetic name) is escaped. The
   test is in Task 2.

### Task 1: The rules — allocation, ageing, statement lines

**Files:**
- Create `domain/billing/ageing.ts` and `domain/billing/ageing.test.ts`.
- Modify `domain/billing/index.ts` (exports).

**Interfaces:**
- Produces:
  ```ts
  export type LedgerEntry =
    | { kind: 'charge'; id: string; reference: string; on: IsoDate; grossFils: Fils }
    | { kind: 'payment'; id: string; reference: string; on: IsoDate; amountFils: Fils; invoiceId: string | null }
    | { kind: 'credit'; id: string; reference: string; on: IsoDate; amountFils: Fils; invoiceId: string };
  export type OpenItem = { invoiceId: string; reference: string; on: IsoDate; openFils: Fils };
  export type OpenItems = { items: OpenItem[]; creditFils: Fils }; // items or credit, never both non-zero
  export type Ageing = { b0to30Fils: Fils; b31to60Fils: Fils; b61to90Fils: Fils; over90Fils: Fils; owedFils: Fils; oldestOpenOn: IsoDate | null };
  export type StatementLine = { on: IsoDate; reference: string; kind: 'charge' | 'payment' | 'credit'; chargedFils: Fils; paidFils: Fils; balanceFils: Fils };
  export function openItems(entries: readonly LedgerEntry[], asOf: IsoDate): OpenItems;
  export function ageing(open: OpenItems, asOf: IsoDate): Ageing;
  export function statementLines(entries: readonly LedgerEntry[], from: IsoDate, to: IsoDate):
    { openingFils: number; lines: StatementLine[]; closingFils: number }; // balances may be negative (credit)
  ```
  `amountFils` is positive for payments and credits; the sign is implied by
  `kind`.

- [ ] **Step 1: Write the failing tests** (names as requirements):
  - `pays the oldest invoice first`: invoices of 100 (Jan 1) and 200 (Feb 1)
    and an unnamed payment of 150 leave 0 and 150 open.
  - `a payment naming an invoice pays that one first`: the same invoices and
    a payment of 150 naming Feb leave 100 and 50 open.
  - `a payment made before its invoice still pays it`: a payment of 300
    (Jan 1) and an invoice of 300 (Jan 5) leave nothing open and no credit.
  - `a credit note clears its own invoice`.
  - `what a named payment or credit note leaves over pays the oldest open invoice`.
  - `a payment naming an invoice that isn't in the ledger joins the pool`.
  - `an overpayment becomes credit and leaves no open invoice`.
  - `entries after the as-at day are ignored`.
  - `buckets by days from the invoice date`: days 30 → 0–30, 31 → 31–60,
    60 → 31–60, 61 → 61–90, 90 → 61–90, 91 → over 90. `owedFils` is the sum;
    `oldestOpenOn` is the earliest open invoice date.
  - `statement lines carry a running balance from the opening balance`:
    entries before `from` make up `openingFils`, lines run in date order then
    reference, and `closingFils` = opening + charged − paid.
- [ ] **Step 2: Run them to see them fail.**
  `npx vitest run domain/billing/ageing.test.ts`. Expected: FAIL, because
  the module doesn't exist.
- [ ] **Step 3: Implement exactly the six-step allocation in the spec.**
  Pool order: unnamed payments, then leftovers, all in date order. Open
  invoices are paid oldest first, by date and then reference. Use `daysBetween`
  from `domain/billing/expiry.ts` for the ages.
- [ ] **Step 4: Run them to see them pass**, then `npx vitest run domain/billing`.
- [ ] **Step 5: Commit.** Message: `feat(billing): open items, ageing and statement lines as pure rules`.

### Task 2: The debtors routes — list and CSV

**Files:**
- Create `app/api/billing/debtors.ts`.
- Modify `app/api/billing/routes.ts` (mount it) and
  `app/api/billing/ledger-schema.ts` (the response schemas).
- Test `tests/billing/db/debtors.test.ts`.

**Interfaces:**
- Consumes: `openItems` and `ageing` from Task 1.
- Produces:
  - `GET /api/billing/debtors?asOf=YYYY-MM-DD` (optional, defaults to
    Dubai's today) →
    `DebtorsResponse = { asOf, totals: { owedFils, b0to30Fils, b31to60Fils, b61to90Fils, over90Fils, inCreditFils, households: number }, rows: DebtorRow[], truncated: boolean }`.
  - `DebtorRow = { clientId, name, mrn, owedFils, b0to30Fils, b31to60Fils, b61to90Fils, over90Fils, inCreditFils, oldestOpenOn }`.
    Rows are sorted by owed, largest first, then by credit, largest first.
    Zero-balance households are left out. At most 50 rows.
  - `GET /api/billing/debtors.csv?asOf=` → `debtors-<asOf>.csv`, with the
    headings `Client, Record number, Owed AED, 0-30 days AED, 31-60 days AED, 61-90 days AED, Over 90 days AED, In credit AED, Oldest open invoice`.
- One SQL read: `app.billing_ledger` rows with `occurred_on <= asOf`,
  left-joined to `payment.invoice_id` and `credit_note.invoice_id` on
  `source_id`, and joined to `client` with `status <> 'erased'`.

- [ ] **Step 1: Write the failing DB tests:**
  - Three households: one current, one with an invoice 45 days old, one in
    credit. Each lands in the right bucket, in the right order.
  - `every household's owed or credit equals its balance in Billing › Balances`:
    compare with `GET /api/billing/clients/:id/balance` `outstandingFils` for
    each seeded household with activity.
  - `the practice total matches the receivable identity`: invoices −
    payments − waived − credit notes, all gross, over households that aren't
    erased.
  - `an erased household is absent` (use `app.erase_client`).
  - `as at a past day ignores later invoices, payments and credit notes`.
  - A practitioner gets 403. Finance, admin and lead practitioner get 200.
  - `each row shown writes one list audit row`; the CSV writes one per row
    plus one `export` row.
  - `a name starting with = is escaped in the CSV`, using a synthetic client
    renamed in the test.
  - More than 50 households with balances gives `truncated: true` and 50
    rows; the totals still cover all of them.
- [ ] **Step 2: Run them to see them fail.**
- [ ] **Step 3: Implement.** Gate on `mayReadInvoices`, validate `asOf` with
  `IsoDate`, compute with Task 1, and audit as the constraints say. Follow
  `app/api/billing/invoices.ts` and the enquiries CSV export.
- [ ] **Step 4: Run them to see them pass**, then the full `pnpm test:db`.
- [ ] **Step 5: Commit.** Message: `feat(billing): the debtors list and its CSV`.

### Task 3: The statement of account PDF

**Files:**
- Create `domain/billing/document/statement.ts`.
- Modify `domain/billing/document/{model.ts, strings.ts, render.ts, index.ts}`.
- Create `app/api/billing/statement.ts`, mounted in `routes.ts`.
- Test `tests/billing/document.test.ts` (extend) and
  `tests/billing/db/statement.test.ts`.

**Interfaces:**
- Consumes: `statementLines` and `ageing` from Task 1.
- Produces:
  - `StatementDocument = { kind: 'statement'; supplier; recipient: Recipient; locale: DocumentLocale; from: IsoDate; to: IsoDate; openingFils: number; lines: StatementLine[]; closingFils: number; ageing: Ageing }`,
    added to the union `renderDocument` accepts.
  - `GET /api/billing/clients/:id/statement.pdf?from=&to=` → `application/pdf`,
    `content-disposition` `statement-<MRN>-<to>.pdf`. The MRN is the record
    number, not a name.
  - `from` and `to` default to the first day of the month two months before
    the current one, through Dubai's today.
  - `from` after `to` is a 400.

- [ ] **Step 1: Write the failing tests:**
  - The domain render contains `Statement of account`, the period, the
    opening and closing balances, every line reference and the four bucket
    figures.
  - The Arabic render contains `كشف حساب`.
  - A household in credit shows the closing balance as credit, not as a
    negative number.
  - In the DB tests: 200 with a PDF for finance; 403 for a practitioner;
    404 for an erased client and for an unknown id; one audit read written;
    the default period applies when no dates are given; `from > to` gives
    400.
- [ ] **Step 2: Run them to see them fail.**
- [ ] **Step 3: Implement.**
  - The layout reuses the invoice's multi-page table geometry and shared
    page blocks, with the columns Date, Reference, Item, Charged, Paid or
    credited, Balance.
  - Supplier details come from the practice, as for invoices.
  - The language is `client.preferred_locale`.
  - Arabic strings get an `OWNER REVIEW` comment.
- [ ] **Step 4: Run them to see them pass**, then `npx vitest run tests/billing domain/billing` and `pnpm test:db`.
