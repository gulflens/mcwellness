## 1. No way to confirm an appointment (scheduling)

`docs/SPEC/scheduling-manual.md` section 3 names the lifecycle in so many
words:

> `confirmed`: client informed (manual toggle in Phase 1; WhatsApp in
> Phase 2).

There is no such toggle. Checked both places it would have to live:

- **The screen.** `app/admin/schedule/SchedulePage.tsx` offers exactly two
  actions per row, "Move" and "Call off"
  (`OPEN_STATUSES = ['proposed', 'confirmed']` gates which rows show them,
  but neither action changes status upward). No third control anywhere on
  the row, the client's own record, or the appointment drawer.
- **The API.** `app/api/appointments/routes.ts` mounts exactly
  `list`, `options`, `create`, `move`, `cancel`, `settings` — no `confirm`.
  `create.ts` accepts no `status` field on the way in (the row is born
  whatever the database default is, which is `proposed`), and
  `move.ts`/`cancel.ts` only ever act on a row already `proposed` or
  `confirmed`; neither one promotes.

**Why it matters beyond the letter of the spec.** `app/api/appointments/
list.ts`'s own `OWN_STATUS_FILTER` — `and a.status in ('confirmed',
'checked_in', 'completed', 'no_show')` — is the query behind a
practitioner's Today. A `proposed` row never appears there, by design
("nobody should be driving to a house that is not expecting them", the
file's own comment). That rule is right. But with no confirm control
anywhere, **every appointment placed through "Add appointment" is
permanently invisible to the practitioner who is meant to drive to it** —
not until the client happens to be told some other way and a developer
manually flips a database column, because that is genuinely the only path
today. This walk only reached a practitioner's Today at all by moving a
pre-existing seeded `Confirmed` row onto today's date; a coordinator
placing a brand-new visit on the calendar has no way to do the same.

Suggested next step for the stream that owns this: read this against
`docs/SPEC/scheduling-manual.md` section 3 and section 4.3 ("New
appointment") and decide the shape of the toggle — a button on the
schedule row, most likely, guarded the way `move`/`cancel` already are
(admin or lead_practitioner, status must be `proposed`, audited).

## 2. The keep-alive script's health check always fails (laptop tooling)

Not a stream's code; recorded because it cost real time during the walk
and will cost the next session the same time unless someone reads this
first.

`.../scratchpad/keepalive.py` (a prior session's, per
`docs/HANDOVER.md` section 5 — "it lives in the session's scratch
directory") runs:

```python
def up(port):
    s = socket.socket(); s.settimeout(1)
    try: s.connect(('127.0.0.1', port)); return True
    except Exception: return False
    finally: s.close()
...
    if not (up(3000) and up(5173)):
        for port in (3000, 5173):
            subprocess.run(['bash', '-c', f'lsof -ti :{port} | xargs -r kill'], check=False)
        time.sleep(1)
        start('laptop-dev', ['pnpm', 'dev'], {})
    time.sleep(60)
```

Vite, at least in this environment, binds port 5173 on the IPv6 loopback
(`[::1]:5173`) only — `curl http://127.0.0.1:5173` refuses the connection,
`curl http://localhost:5173` (which resolves `::1` first) answers 200. So
`up(5173)` is always `False`, the `and` is always `False`, and the script
kills whatever is listening on 3000 and 5173 and restarts `pnpm dev` —
**every single minute, forever**, whether or not anything was actually
wrong. `keepalive.log` shows exactly that: "restarted laptop-dev" once a
minute, continuously, from 05:06 through to when this walk finished after
07:00, with no gap.

**Effect on this walk:** repeated `net::ERR_CONNECTION_REFUSED` and `502
Bad Gateway` on ordinary API calls mid-session, and — because a killed
`pnpm dev` process drops Vite's dev-server websocket, and Vite's own
client reloads the page when that connection is lost and later restored —
open drawers, forms and in-progress typing were silently discarded roughly
once a minute throughout. Every multi-step flow in this walk (recording an
assessment, drafting a report, running a session) had to be re-attempted
inside the roughly fifty-five-second windows between restarts.

Suggested next step: whoever owns that script changes the check to
`up('localhost', port)` (or explicitly probes `::1`) instead of
`'127.0.0.1'`, or drops the liveness check for 5173 in favour of an HTTP
probe against `/` the way the staging half of the same script implicitly
gets right by checking a port a server actually answers on. This is
laptop-only; nothing in the shipped app depends on `127.0.0.1` versus
`localhost`.

## 3. Progress report: "fewer than two brain maps" with two on file (reports)

`docs/SPEC/reports-v1.md` section 2 promises "the brain-map comparison
where two or more assessments exist". Reproduced on a client with two
Brain map assessments recorded and attached (proved to genuinely be two by
the Assessments tab's own "Compare" screen finding and comparing them
correctly): the progress-report draft's "Brain maps" section reads

> This client has fewer than two brain maps of one kind, so the report
> says nothing about them.

Tried with the report's own coverage dates both left blank and set to
2026-08-01–2026-09-06 (spanning both assessments' date); no change. Screen:
Reports tab → "Write a progress report". Worth checking whether the
report's own brain-map count query filters by something the Compare
screen's query does not — a status, a coverage-date join, or a different
notion of "one kind" than "same instrument".

## 4. Client search fails on a full display name (client-record)

The search box captioned "Name, record number or Emirates ID" — used both
on the Clients list and inside "New appointment"'s client picker — answers
"No client matches" for `Dahlia Bay` (the client's own displayed name,
typed exactly, with the space a real user would type). `Dahlia` alone
matches; `MW-000005` alone matches. Reproduced twice, in two different
booking attempts. Worth checking whether the query tokenises on the
family name at all, or matches only a single unbroken token against
`given_name`/`family_name` separately rather than the concatenation a
user sees on screen.

## 5. Late-notice penalty applies to a still-uninformed visit (scheduling)

`docs/SPEC/scheduling-manual.md` section 3: "`proposed`: placed on the
calendar, client not yet informed." Yet calling off a `proposed`
appointment inside 24 hours of its window shows exactly the same warning a
`confirmed` one would — "This is inside the practice's 24 hours' notice, so
it uses one of the client's sessions. It can be waived afterwards." — and
offers **"The family called it off"** in the reason list, which cannot be
true of a visit nobody has told the family about yet.

`domain/scheduling/cancellation.ts`'s `isLateCancellation` takes the
appointment and the cancellation time and the notice period; it does not
take the status, so a `proposed` row and a `confirmed` row are judged
identically. Whether this is the intended design (a coordinator holding a
slot inside the notice window, then releasing it, is arguably not "late"
in any sense the household experiences) is a call for the stream, not
this walk; recorded because the copy shown to the coordinator
("the family called it off") states something false in the `proposed`
case specifically.

## 6. "added a appointment" (trunk)

`domain/shared/audit-narrative.ts`, the generic `insert` fallback (around
line 828):

```ts
case 'insert':
  return pick(t(`${actor} added a ${entity}`, `${actor} أضاف ${entity}`), locale);
```

`entity` for `event.entityType === 'appointment'` renders as
"appointment", giving "Hazel Harbour added a appointment" on the client
Timeline. English needs "an" before a vowel sound; the Arabic half is
unaffected (no article to choose). A small `startsWithVowelSound(entity)`
check, or a specific case for `appointment` the way `client.erase` already
gets one just above this branch, would fix it without touching every
other entity that already reads correctly with "a".

## 7. The client-portal seed people are not on this laptop's database (trunk / whoever reseeds)

Neither seeded "Client contact" — Dahlia Bay nor Clover Quarry — can sign
in through the laptop's own sign-in door. Clicking either leaves the
screen on `/sign-in` with nothing said; the network tab shows `GET
/api/me` answering 403.

Traced with a direct, read-only query against the laptop's own local
database (`postgresql://postgres:postgres@localhost:5432/postgres`, the
value already in this checkout's own `.env`):

```
select id, auth_id, status, display_name from app_user
 where display_name in ('Dahlia Bay','Clover Quarry','Hazel Harbour');
```

returns **one row** (Hazel Harbour) of the three. `app.resolve_actor`
(`db/migrations/095_actor.sql`) returns no row when `app_user.auth_id`
does not match, which is exactly what a 403 from the request-context
middleware means (`app/api/_middleware/request-context.ts`,
`forbidden()`). Meanwhile `GET /api/dev/session` lists both contacts by
name, because that route calls `generateSeed()` fresh, in memory, from
whatever `db/seed/generate.ts` says today — it never reads the database.
So the sign-in door offers two people the database has never heard of.

`docs/STAGING.md`'s own seventh-pass entry records exactly this addition
landing in `db/seed` — "two `app_user` rows (Clover Quarry, English;
Dahlia Bay, Arabic)" — as something staging had to be caught up to
separately. The laptop's own database looks to be in the same position
staging was in before that pass: migrated, but not reseeded since. Two
more things seen in passing point the same way and are not filed as
separate items: the Kit register is completely empty (piece eight's
"done when" names one amplifier per practitioner and one overdue,
unassigned one), and the client portal's own Home screen reads "The
practice has not recorded a WhatsApp number" although `docs/STAGING.md`
records `tenant.whatsapp_number` being set on the seed practice.

Not filed as a code defect against any stream on the evidence gathered —
this looks like the laptop needing the same kind of catch-up
`docs/STAGING.md` walks through for the hosted project, not a bug in the
client-portal feature itself. The actual invite-and-redeem door
(`docs/SPEC/client-portal.md`'s own "the door") works correctly end to
end and was used for the rest of this walk instead. Recorded here so
whoever next reseeds the laptop's database — or decides the dev
sign-in door should read the database instead of the in-memory seed list
— has this written down rather than rediscovering it.

## Requested: an Arabic vocabulary for the five bands, in `domain/shared`

**Not this round's to build, and not one stream's to own.** An Arabic
progress report prints "Fz Alpha" in Latin script inside an Arabic table.
That is honest — nothing is blank and nothing reads "null" — but a household
reading their own report in Arabic meets five English words in the one column
that is theirs.

The reason is that the five band names exist twice, in English only, in two
streams' own files: `BAND_LABELS` in `app/admin/assessments/copy.ts`, which
the comparison screen renders, and `BAND_WORDS` in
`app/api/reports/gather.ts`, which quotes it rather than importing it because
`docs/SPEC/OWNERSHIP.md` rule 3 forbids a route reaching into another
stream's folder. Neither has an Arabic half, and neither is the place to
invent one: whichever added it first, the other would copy it, and two copies
of a vocabulary drift.

**The request.** A band vocabulary in `domain/shared` — the five bands, each
with its English and Arabic word, and the units beside them for the same
reason — read by the comparison screen and by the report route, so both name
a band from one place. `domain/shared` is where rule 3 says a type two
modules need belongs, and the precedent is `fileSignature.ts`, which the
trunk's round 31 moved there for exactly this reason. Then `gather.ts` fills
`labelAr` instead of leaving it null, and nothing in the renderer changes at
all: `domain/reports/document/render.ts` already prefers `line.labelAr` over
`line.label` when the page is right-to-left, and the null-`labelAr` fixture
in `tests/reports/document.test.ts` already exercises both sides of that
choice.

**Whose.** The trunk's, because the file is `domain/shared`'s and two streams
read it; the Arabic words themselves are the operator's to approve, as every
Arabic string in this repository is. The site is not part of this: an
electrode site is written in the international 10-20 system in every
language, so "Fz" is already the Arabic word for Fz.
